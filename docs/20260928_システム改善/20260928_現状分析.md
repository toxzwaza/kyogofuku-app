# kyogofuku-app 現状分析（2026-09-28）

Phase 0 の成果物。コード調査にもとづく現状把握と、「全員が使いやすい」観点での課題整理。
※ 本書はコードから読み取った事実ベース。現場の実感はヒアリング（Phase 1）で補完する。

## 1. システム規模の現状

| 指標 | 現状 | 所感 |
|------|------|------|
| ドメインモデル | 50以上 | 予約・顧客・LINE・勤怠・給与まで担う基幹システム |
| 管理画面ページ | 182 Vue コンポーネント | 機能が非常に多く、全体像の把握が難しい規模 |
| サイドバーメニュー | 10グループ・38項目 | 1画面のメニュー数として多め。特に勤怠が8項目 |
| 最大ページの行数 | Dashboard.vue 6,340行 / 顧客一覧 1,449行 | 1ページに機能が集中しており保守・表示速度に懸念 |

**評価**：機能は十分すぎるほど揃っている。次のステップは「機能追加」より **「今ある機能を、誰でも迷わず使える形に整える」** ことが本筋。

## 2. 「使いやすさ」を阻害している主な課題

調査で判明した課題を、影響度と対策コストで整理した。

### 🔴 最優先（年配者に直接効く・低〜中コスト）

| # | 課題 | 根拠 | 対策の方向性 |
|---|------|------|------------|
| A | **文字が小さすぎる** | `text-xs`(≒11px) が1,796回、`text-sm`(≒13px) 併せ5,212回。ラベル・説明・表・ボタン全般 | Tailwind の基本サイズを引き上げ、`text-xs`→`sm`、`sm`→`base` へ段階置換 |
| B | **ツールチップが年配者に届かない** | `Tooltip.vue` が11px・ホバーのみ。タブレット/スマホでは表示すらされない | ツールチップ依存をやめ、説明を画面に常時表示（13px以上） |
| C | **補足説明が小さく読めない** | フォーム補足が `text-[11px]`/`[10px]` | ラベル直下に常時表示・サイズ確保。項目の相互関係は図解 |
| D | **押しにくい・押し間違える** | 標準ボタン h-9(≒36px)、チェック/ラジオも小さい | タッチ要素を44px以上に。重要操作は大ボタン化 |

### 🟠 次点（構造の分かりやすさ・中コスト）

| # | 課題 | 根拠 | 対策の方向性 |
|---|------|------|------------|
| E | **メニューが多く迷う** | 38項目・勤怠だけ8項目 | よく使う順の並べ替え、勤怠のサブグループ化、各項目に用途の一言 |
| F | **一覧の絞り込みが複雑** | 顧客一覧はフィルタタブ6種・各5〜10項目 | 「かんたん検索」と「詳細検索」を分離。初期表示はシンプルに |
| G | **表の列が多くモバイルで横スクロール必須** | 一覧6列＋`overflow-x-auto`が155ファイル | 端末幅で列を自動間引き、行タップで詳細へ（既に一部実装済み） |
| H | **ダッシュボードが新旧併存で混乱** | `admin.overview`(新) と `Dashboard.vue`(旧6,340行) | 新版に一本化。「今日やること」が一目で分かるトップに再設計 |

### 🟡 中期（体験の底上げ・高コストまたは新規開発）

| # | 課題 | 根拠 | 対策の方向性 |
|---|------|------|------------|
| I | **画面内でマニュアルに辿れない** | マニュアルは6本あるが別ページ。操作中に開きにくい | 各画面から「この画面の使い方」に1タップで飛べる導線 |
| J | **アクセシビリティ不足** | `aria-label`は77件どまり・コントラスト未検証 | 主要導線のコントラスト・キーボード操作を WCAG AA 基準へ |
| K | **AI機能は未実装** | app配下に AI 連携なし（概要分析の「経費予測AI」は現状コードに存在せず） | 効果の明確な箇所に限定導入（→ 3章） |

## 3. AI 導入の検討（現時点の見立て）

現状 AI は一切入っていない。**「AIありき」ではなく、手作業や待ち時間が明確に減る箇所** に絞って導入するのが得策。社内では既に AIアバター研修・議事録・Q&A で Claude 運用実績があり、技術的な土台はある。

効果が見込めそうな候補（ヒアリングで裏を取る）：

| 候補 | 効く場面 | 期待効果 | 難度 |
|------|---------|---------|------|
| **LINE返信の下書き生成** | 顧客への返信文作成 | 文面作成の時短・品質均一化。人が確認して送信 | 低〜中 |
| **顧客メモ/やりとりの要約** | 顧客詳細を開いた時 | 過去経緯を一読で把握、引き継ぎが楽に | 中 |
| **紙・手書きの写真取り込み（OCR）** | 紙メモ・書類の入力 | 転記の手間削減。社内にOCR運用実績あり | 中 |
| **画面内AIヘルプ（操作質問）** | 操作に迷った時 | マニュアルを探さず解決。研修Q&A基盤を流用可 | 中 |
| **自然文で画面を呼び出す** | 「〇〇の予約を見せて」 | 導線短縮。ただし年配者の効果は要検証 | 中〜高 |

いずれも **人が最終確認する前提**（誤りを自動で確定させない）を基本とする。

## 4. 技術面の健全性メモ

- Laravel 9 / PHP 8.2 / Vue3(Inertia) / Tailwind と構成は標準的で、改修の土台は良好。
- ただし巨大化したページ（Dashboard 6,340行等）は、改修前に分割整理が必要になる可能性。
- 文字サイズ・ボタンサイズは Tailwind 設定と共通コンポーネント（Button.vue 等）に集約されているため、**全体の底上げは比較的少ない箇所の変更で波及させられる**（費用対効果が高い）。

## 5. Phase 0 の結論

1. 最も費用対効果が高いのは **A〜D（文字・ボタン・説明の底上げ）**。共通設定への変更で全画面に効く。まずここから。
2. **E〜H（構造の分かりやすさ）** は現場の使い方に依存するため、ヒアリング（Phase 1）で優先順位を確定する。
3. **AI（K）** は限定導入。LINE返信下書き・要約・OCR・画面内ヘルプが有力。ヒアリングで需要を確認。
4. 大改修は繁忙期（12〜3月）を避け、それまでに底上げ系を先行させる。
