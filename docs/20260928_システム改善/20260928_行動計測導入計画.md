# 行動計測（Microsoft Clarity）導入計画（2026-09-28）

> **【保留】2026-09-28：GTM・Clarity の導入は一旦保留。** 本計画は再開時のために保管する。

Phase 1 を「現場ヒアリング」から **「行動計測でデータドリブンに課題特定」** へ変更。

## 背景・ねらい

現場スタッフにヒアリングしても「何が使いづらいか」を本人が言語化できていない印象がある。
そこで **実際の操作行動をデータで可視化** し、詰まりどころを客観的に特定する。
特に年配スタッフが「どこで手が止まっているか／押しても反応しない場所を押していないか」を見たい。

これにより `改善候補リスト.md` の優先度を、感覚ではなく **実データで確定** できる。

## ツール選定

| ツール | 役割 | 位置づけ |
|--------|------|---------|
| **Microsoft Clarity** | ヒートマップ・セッション録画・行動インサイト | 中心。無料・機能十分 |
| Google Tag Manager (GTM) | タグ管理（計測タグの出し入れ） | 併用は任意（→ 後述） |

### Clarity で分かること（本件で特に有用）
- **ヒートマップ**：どのボタン・項目がよく押されるか／全く押されないか
- **セッション録画**：実際の操作を再生（迷い・やり直し・離脱が見える）
- **レイジクリック**：同じ所を苛立って連打（＝反応が遅い／分かりにくい箇所）
- **デッドクリック**：押しても何も起きない場所を押している（＝押せると誤認する要素）
- **クイックバック**：開いてすぐ戻る（＝目的の画面でなかった＝導線が悪い）
- **画面別の利用頻度**：どの画面がよく使われ、どこが使われていないか

### GTM を併用するか
- 管理画面はマーケサイトのようにタグを頻繁に増減しないため、**GTM の必要性は高くない**。
- Clarity は GTM 経由でも直接埋め込みでも導入できる。将来 GA4 等も足す可能性を見込むなら GTM 経由が拡張しやすい。
- **推奨**：まずは Clarity を直接埋め込みで最短導入。GTM は将来必要になった時点で。
- ※ 判断は村上さんに委ねる（下の「承認事項」参照）。

## ⚠ プライバシー設計（最重要・本件の肝）

本システムは **顧客の個人情報（氏名・住所・電話・LINE・契約情報）が画面に大量表示** される基幹システム。
Clarity のセッション録画は画面を Microsoft（米国）に送信するため、**無対策での導入は不可**。

### 必須の対策
1. **マスキングは Strict モード（全テキストをマスク）**
   - 公式が金融・医療・法律など機微データ扱いサイトに Strict を推奨。本件も該当。
   - Strict では画面構造・クリック位置・操作フローは取れるが、**文字情報は伏せられる** → 使いやすさ分析には十分。
   - 入力欄の中身は全モードで常にマスクされる（仕様）。
2. **追加マスク**：顧客名・電話等の要素に `data-clarity-mask` 属性 or `clarity-mask` クラスを付与し二重に保護。
3. **計測対象の限定**：まずは公開ページを除外し、**管理画面のみ**を対象（改善したいのは管理画面のため）。
   逆に顧客個人情報が特に濃い画面（顧客詳細等）は初期は除外も検討。
4. **平田側への説明・同意**：顧客データを外部ツールが（マスク前提でも）扱う点を平田側に説明し了承を得る。
   必要ならプライバシーポリシー・利用規約の記載も確認。
5. **計測期間を区切る**：常時ではなく「課題特定のための一定期間」限定運用も選択肢。

→ この設計により「個人情報は送らず、操作行動だけを取る」構成にできる。

## 技術実装（Inertia.js / SPA 対応）

本システムは Inertia.js（SPA的挙動）。**画面遷移でスクリプトが再実行されない**ため、素の埋め込みだと
2画面目以降が正しく計測されない既知の問題がある（セッションが切れる／URLが更新されない）。

### 対応方針
1. Clarity トラッキングコードは共通レイアウト（`app.blade.php`）に1度だけ設置。
2. Inertia のページ遷移イベント（`router.on('navigate')` 等）で、遷移のたびに
   Clarity へ現在の画面を通知（カスタムタグ／`clarity('set', ...)`）し、画面別に集計できるようにする。
3. 主要画面には **画面識別のカスタムタグ**（例：顧客一覧／予約詳細）を付与し、
   「どの画面で詰まっているか」を画面単位で分析できるようにする。
4. 開発環境で遷移・マスク・画面識別が正しく効くことを確認してから本番投入。

## 計測設計（何を見て何を判断するか）

| 見る指標 | 読み取ること | 改善候補への反映 |
|---------|------------|----------------|
| レイジ／デッドクリック多発箇所 | 反応が遅い・押せると誤認・分かりにくいUI | 最優先で該当画面を改修 |
| よく使われる画面 TOP | 底上げ（文字・ボタン拡大）の効果が大きい画面 | グループ1の適用順を決める |
| 使われていない画面・メニュー | メニュー整理・統廃合の候補 | N1（メニュー整理）の判断材料 |
| クイックバック多発の導線 | 目的地に一発で辿り着けていない | N1〜N3（構造）の優先度 |
| 録画で見える「迷い・やり直し」 | 具体的な操作のつまずき | 個別画面の改修内容を具体化 |

## 進め方

1. **導入準備**：Clarity プロジェクト作成 → Strict マスク設定 → 追加マスク実装 → SPA対応実装（開発環境で検証）
2. **平田側合意**：プライバシー設計を説明し了承を得る
3. **本番投入**：管理画面に計測開始（承認後）
4. **データ収集**：一定期間（例：2〜4週間、繁忙前の実業務が回る期間）
5. **分析**：上表の指標で詰まりどころを特定
6. **優先度確定**：`改善候補リスト.md` の優先順位を実データで更新
7. **改善着手**：底上げ系（グループ1）＋データで判明した高効果箇所から
