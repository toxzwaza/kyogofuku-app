# ケア優先度＆ネクストアクション提案 機能設計（2026-09-28）

オーバービューに「今日ケアすべき顧客・予約」を優先度順で表示し、各件にAIが**次の一手（ネクストアクション）**を提案する機能。
A8（成約分析）・A7（返信漏れ防止）・A2（返信下書き）を束ねる **顧客ケアの司令塔**。

## この機能が解決すること

- 年配スタッフを含め、**ログインして最初の画面で「今日やること」が優先度順に分かる**。
- 「成約見込みが高いのに放置されている顧客」＝**機会損失を可視化**し、取りこぼしを防ぐ。
- 現状分析の課題「オーバービューが活用されていない」も同時に解決。

## 中核の考え方：ケアスコア

**ケアすべき ＝ 成約見込み × 放置度 × 緊急度**（見込みが高いのに手が付いていないほど優先）

| 要素 | 使うデータ（分析で有効と確認済み） |
|------|--------------------------------|
| **成約見込み** | 流入元の濃さ（HP_TOP/紹介/DM＝濃い）・検討プラン・来店動機・リードタイム（成人式2〜3年前）・来店歴 |
| **放置度** | 最終接触からの経過日数・未返信・予約対応ステータス |
| **緊急度** | 受信内容（キャンセル/クレーム/急ぎ＝AI判定）・期限接近（前撮り/成人式/残金期日） |
| **除外（スコア0）** | 既に成約完了で対応不要・対象外（**浜店/好一の別ブランド**）・キャンセル済み |

→ 分析で得た**勝ちパターンを優先度ロジックに実装**する。データが整うほど精度が上がる。

## ネクストアクション提案（AI）

対象の状態から「次にすべき一手」を提示。ルールで候補を出し、**AIが文脈に合わせて具体的な文面・理由**に落とす。

| 状態 | ネクストアクションの例 |
|------|----------------------|
| 未返信で数日経過 | 「◯日未返信。濃いリード（HPトップ経由）なので今日中にLINEで返信を」 |
| 来店予約のみ・未来店 | 「来店案内・日程確認の連絡を」 |
| 顧客化済み・前撮り未設定 | 「前撮り日程の提案を」 |
| 残金期日が近い | 「残金支払い（成約日から10営業日）の案内を」 |
| 成人式が近い・準備未完 | 「お支度時間・当日案内の確認を」 |

各提案から**ワンタップで A2（返信下書き）へ**進めるようにし、実際の連絡までを短縮する。

## オーバービュー表示イメージ

```
─ 今日のケアリスト（あなたの担当 / 店舗）──────────────
🔴 山田様  HPトップ・2027成人式  4日未返信  [ケア度92]
        → 濃いリード。今日中にLINEで来店案内を   [下書きを作る]
🟠 佐藤様  紹介・前撮り未設定    前撮り3ヶ月前  [ケア度78]
        → 前撮り日程の提案を                    [下書きを作る]
🟡 …
────────────────────────────────────────────
```

- 優先度順のカード。顧客名・状態サマリー・経過・ケア度・ネクストアクション・下書きボタン。
- 店舗／担当でフィルタ。緊急は赤バッジ。上位N件（下は「もっと見る」）。
- 年配者向け：文字大きめ・タップ領域44px以上（モバイル改善と統一）。

## 技術構成

1. **スコアリング＆提案バッチ（cron）**：アクティブな予約/顧客を定期的にスコアリング。
   見込みありの対象について AI がネクストアクション文を生成 → `care_suggestions` テーブルに保存。
   ※ 社内 cron 運用実績あり。AI は Bedrock 経由推奨。
2. **オーバービュー**：保存済みの結果を読むだけ（画面は高速・AIをリアルタイム呼び出ししない）。
3. **A2 連携**：カードの「下書きを作る」から返信下書きへ。
4. **コスト管理**：AI対象を「見込みあり×要対応」に絞る＋キャッシュ＋上限設定。

## 注意点

- **人が最終判断**：提案であり自動実行しない（連絡は人が確認して送信）。
- **薄いリードを切り捨てすぎない**：見込み判定は誤りうる。低スコアも「見送り」でなく下位表示に。
- **対象外の除外**：浜店・好一（別ブランド）は対象から外す（分析8-1参照）。
- **データ品質依存**：顧客紐づけ・ステータス運用・表記揺れの整備で精度が上がる。

## 拡張構想：キャンセル防止フォロー（維持ケア）【村上要望 2026-09-28】

第1段は「成約前リードの獲得ケア」。これに **「成約後顧客の維持ケア（キャンセル防止）」** を追加する。
＝第1段で除外した成約済み顧客を、別目的（キャンセルさせない）で対象にする。

### データ根拠（localdb_prod 実測）
- フォロー対象：確定成約済み×成人式がこれから ＝ **約1,964人**
- キャンセルは成約後すぐでなく **中央値50日・平均159日** で発生 → 成約後1〜数ヶ月の関係維持が肝
- キャンセル29件中 **前撮り前が16件** → 前撮り後は固まりにくい（キャンセル料も前撮り後100%）
- 前撮り状況：未設定957・予定528（＝前撮り前がリスク高1,485）・済み493
- ⚠ LINE未連携が1,585人 → LINEフォローには連携促進もセットで必要

### キャンセルリスクスコア（高いほど手厚くフォロー）
- 前撮り状況（未設定 ＞ 予定 ＞ 済み）
- 成約からの経過（クーリングオフ〜低キャンセル料期間ほど離脱容易）
- 最終接触からの経過（音信不通が長いほど関係希薄）

### 定期フォローの節目（キャンセル料体系＋実データ）
| タイミング | フォロー内容 | next_action_type |
|---|---|---|
| 成約直後（8日クーリングオフ） | お礼＋安心のご連絡 | thanks |
| 成約1ヶ月前後（キャンセル多発期） | 近況伺い・関係維持 | followup |
| 前撮り日が未設定のまま | 前撮りのご案内 | photo |
| 前撮り前・成人式前 | 準備の確認連絡 | prep |

### 実装方針（A9への統合）
- `care_suggestions.subject_type` に区分を持たせる：`acquisition`（獲得）/ `retention`（維持）。
- 同じバッチ（care:generate）で獲得ケア＋維持ケアの両方を生成。
- オーバービューで「獲得／維持」を切り替え表示（または2セクション）。
- AIは節目検知＋リスクスコア＋フォロー文面の下書き（送信は人が確認）。
- 運用：LINE未連携者への連携促進を並行すると維持ケアの効率が上がる（下記）。

→ 実装は第1段（獲得ケア）のレビュー後、続けて着手可能。

### LINE連携促進メール（維持ケアの前提整備）【村上要望 2026-09-29】

維持ケアをLINEで回すため、LINE未連携の成約者へ**メールで連携を促す**。

**対象規模（重要な制約）**
- 成約済み×成人式未来×LINE未連携 ＝ 1,585人。**うちメールありは299人のみ**。
- メールなし1,286人には店頭・電話・DMで案内するしかない（システム外運用）。
- customers.email 保有率は全体35%。→ **連携促進の効果を広げるには、まず顧客のメール取得率向上が課題**。

**既存部品の流用（新規開発は小さい）**
- **予約確認メール(`ReservationConfirmationMail` / `reservation_confirmation.blade.php`)が既にLINE連携リンクを内包**。
- LINE連携リンク＝`CustomerLineLinkToken`（UUID・有効期限・使用済み管理）。`issueLineLiffUrl()` の顧客版を作る。
- メール記録は `Email`/`EmailThread`、送信は `Mail::to()->send()`（SES）。一括送信の重複防止思想は `LineBroadcastSender` を参考に。

**新規に作る部分**
- `LineIntroductionMail`（連携案内専用Mailable）＋テンプレ（連携メリット＋ワンタップ連携リンク中心）
- 対象抽出（成約×成人式未来×LINE未連携×メールあり）
- 一括送信Job（キュー・重複防止・送信ログ）
- 効果測定（連携率＝送った人のうちLINE連携に至った割合）

**運用の注意（本番のお客様へ送信）**
- 内容承認 → テスト送信 → 段階送信（一斉送信は慎重に）。
- 配信停止・二重送信防止を必ず入れる。送信は人の承認後。
