# AI 活用計画（2026-09-28）

kyogofuku-app への AI API 連携で実装できる機能の検討資料。
`改善候補リスト.md` グループ4 を具体化したもの。

## 基本方針

- **「読む量・打つ量・探す手間を減らす」** ものを優先。これは年配スタッフに最も効く。
- **人が最終確認**：AI は下書き・要約・提案まで。送信・確定・登録は必ず人が行う。誤りを自動確定させない。
- **既存データ・既存機能を活かす**：本システムには対応履歴・LINE/メール・アンケート・申込書・契約情報が
  既に蓄積されており、AI と組む素材が揃っている。
- **社内実績を流用**：Claude API（研修Q&A）・whisper（音声）・OCR は社内で稼働実績あり。ゼロからではない。

## AI 連携先の選択肢

| 選択肢 | 特徴 | 個人情報の扱い |
|--------|------|--------------|
| **Claude API（Anthropic 直接）** | 社内実績あり・導入最短。テキスト/画像対応 | API送信データは既定で学習に使われない |
| **Amazon Bedrock 経由（Claude）** | 国内リージョン処理・AWS内で完結。本番はAWS(RDS)基盤 | 学習不使用・データ境界が明確で説明しやすい |
| whisper（音声→文字） | 社内で稼働中。ローカル処理可 | ローカル完結にできる |

→ **顧客個人情報を扱う機能は Bedrock 経由を軸に検討**（平田への説明がしやすい）。
　軽い文章生成やヘルプは Claude API 直接でも可。最終判断は平田の顧客データ方針に合わせる。

## 実装候補（優先度順）

### ⏸ 保留：顧客サマリー自動生成（旧A1）
- **内容**：顧客詳細を開くと、メモ・LINE/メール履歴・契約・前撮り状況を AI が3行程度に要約表示。
- **状況**：2026-09-28 **一旦保留**。再開時はこの節を参照。
- **使うデータ**：`Customer` `CustomerNote` `CustomerLineMessage` `Email/EmailThread` `Contract` `PhotoSlot`
- **API**：Claude（Bedrock 経由推奨）／ 難度：中 ／ コスト：1顧客要約あたり数円

### 🥈 第2候補：LINE / メール返信の下書き生成
- **内容**：顧客への返信を、過去のやりとり・契約状況・規約を踏まえて AI が下書き。スタッフが確認・修正して送信。
- **効く場面**：日々の顧客対応。文面作成の時短と品質の均一化。
- **年配者への効果**：★★☆（「打つ量を減らす」。文章作成の負担が大きい人ほど効く）
- **使うデータ**：`CustomerLineMessage` `Email` `Customer` `Contract` 規約テンプレート
- **API**：Claude（Bedrock 経由推奨）
- **難度**：低〜中　／　**概算コスト**：1下書きあたり数円
- **注意**：**自動送信は絶対にしない**。送信ボタンは人が押す。金額・日程など重要事実は原文確認を促す。

### 🥉 第3候補：返信漏れ防止バッチ（AIサポート）【目玉・村上要望】
- **内容**：定期バッチが「顧客から受信したのに未返信のまま一定時間経過した LINE/メール」を自動抽出し、
  各件を AI が判定（①本当に返信が必要か ②緊急度 ③内容の要約 ④推奨アクション）。
  結果を管理画面の「**要対応リスト**」に表示し、担当者へ通知して**返信漏れをゼロに近づける**。
- **効く場面**：繁忙期の問い合わせ集中時、担当不在・引き継ぎ時、休み明け。人の記憶頼みをやめる。
- **年配者への効果**：★★★（見落とし・対応漏れの不安を解消。システムが先回りして気づかせる）
- **仕組み**：
  1. cron で定期実行（例：営業時間中1時間ごと）。※社内 cron 運用実績あり（`docs/CRON_SETUP.md` 等）
  2. 未返信判定：顧客/予約からの最新受信が自社の最終返信より新しく、かつ設定時間（例：3時間/翌営業日）経過。
     `customer_line_messages.admin_read_at` の未読情報も活用（概要分析より）
  3. AI 判定：スタンプ・「ありがとう」等の終話や返信不要を除外し、要返信のみを緊急度付きで抽出＋要約
  4. 表示・通知：管理画面「要対応リスト」＋担当へ通知（既存の LINE通知拡張 / AkiTalk Teams通知を流用）
  5. A2（返信下書き）と連携：要対応リストから**ワンタップで返信下書きへ**進める
- **使うデータ**：`CustomerLineMessage`（`admin_read_at`）`Email/EmailThread` `EventReservation` `Customer`
- **API**：Claude（Bedrock 経由推奨）　／　**難度**：中　／　**概算コスト**：1巡の判定で数十円〜（対象件数×1円未満）
- **注意**：
  - あくまで**サポート**。「返信不要」判定で本当は必要な連絡を隠さないよう、除外は保守的に（迷ったら要対応に残す）。
  - 誤検知の許容ラインと通知のしつこさ（頻度・宛先）は現場と調整。担当割当のロジックも要確認。
  - A4（受信仕分け）の分類結果を優先度判定に流用できるため、A4 とセットで設計する。

### 第4候補：受信メッセージの自動仕分け（返信漏れ防止バッチと連携）
- **内容**：受信した LINE/メールを「予約変更・キャンセル・問い合わせ・クレーム・その他」に自動分類し、
  タグ付け＋優先度表示。`line_unknown_inbound_messages` の振り分けにも。返信漏れ防止バッチの優先度判定の土台。
- **効く場面**：対応の見落とし防止、優先度の高い連絡に早く気づく。
- **年配者への効果**：★★☆（「探す手間を減らす」）
- **使うデータ**：`CustomerLineMessage` `Email` → 分類ラベル → `CustomerTag` 等
- **API**：Claude　／　**難度**：低〜中　／　**概算コスト**：1件あたり1円未満

### 第5候補：画面内 AI ヘルプ
- **内容**：管理画面から「この画面どう使う?」と質問すると、マニュアルに基づき回答。マニュアルを探さなくてよい。
- **効く場面**：操作に迷った時。人に聞かないとできない作業の自立支援。
- **年配者への効果**：★★☆（「探す手間を減らす」）
- **使うデータ**：既存の業務マニュアル（`Pages/Admin/Manuals/`）を知識源に
- **API**：Claude（研修Q&A基盤を流用可）　／　**難度**：中

### 第6候補：成約パターン分析 → 回答サポート（A8）【村上要望】
- **内容**：過去の**成約データ**を分析して「何が成約に効いたか（勝ちパターン）」を把握し、
  それを対応中の顧客への提案・返信のサポートに活かす。**2段構え**で進める。
- **効く場面**：接客・提案・返信の質を、経験の差によらず底上げしたい時。
- **年配者への効果**：★★☆（ベテランの勝ちパターンを誰でも使える＝経験差の補助）

#### ステップ1：成約要因の分析（土台・AIなしでも実施可）
- 成約（`Contract`）と非成約の予約・顧客を比較し、成約に効いた要因を抽出：
  - 流入元（UTM）別の成約率
  - 初回接触〜成約までの**対応回数・返信スピード**との関係
  - 前撮り提案の有無・プラン・エリア・時期・担当者による差
- やりとり（`CustomerLineMessage` `Email` `CustomerNote`）から、成約会話の特徴・有効な提案トークを抽出
- 手段：集計分析（SQL / Python）＋必要に応じAIでテキスト傾向抽出

#### ステップ2：回答サポートへの実装
- 過去の成約事例を検索できる形（RAG）にし、対応中の顧客に近い**成功事例のアプローチを提示**
- A2（返信下書き）に「成約に効いたトーン・提案・タイミング」を織り込む → **成約率を意識した下書き**へ
- **使うデータ**：`Contract` `EventReservation`（UTM・担当・日程）`Customer` `CustomerNote` `CustomerLineMessage` `Email` `PhotoSlot`
- **API**：分析=集計＋Claude／サポート=Claude＋ベクトル検索（RAG、Bedrock 経由推奨）
- **難度**：中〜高　／　**概算コスト**：分析は一時的、サポートは1提案あたり数円
- **注意（重要）**：
  - **データ量・質が精度を決める** → 着手前に成約件数・やりとりの蓄積量を確認する（下記「前提調査」）
  - **相関≠因果**：分析結果は仮説として扱い、現場感覚と突き合わせる
  - **交絡に注意**（例：ベテランが良い顧客を担当していただけ、等）
  - 個人情報は集計・匿名化ベース。AI へ渡すのは最小限に

#### A8 の前提調査（着手前にやること）
- ローカル同期済み DB で、成約件数・成約/非成約の比率・やりとりのテキスト蓄積量を集計し、
  分析に耐えるデータ量があるかを判定する（個人情報は件数・集計レベルの確認に留める）。

## 進め方（提案）

採用5機能を、依存関係と効果で3段階に分けて進める。

| 段階 | 機能 | ねらい |
|------|------|--------|
| 第1段：受信管理の強化 | **A4 受信仕分け → A7 返信漏れ防止バッチ** | 目玉。まず「漏らさない」土台を作る。A4の分類をバッチの優先度判定に使うためセットで |
| 第2段：個別対応の支援 | **A2 返信下書き** | 「打つ手間」を削減。要対応リストから下書きへ繋ぐと相乗効果 |
| 第3段：自立支援 | **A5 画面内ヘルプ** | 独立して追加可能。研修Q&A基盤を流用 |
| 並行：分析→サポート | **A8 成約パターン分析→回答サポート** | まず前提調査(データ量確認)→分析→勝ちパターンをA2に織り込む。データ量次第で時期調整 |

1. **PoC**：第1段（受信仕分け＋返信漏れ防止バッチ）を開発環境で小さく作り、判定精度と通知の使い勝手を確認。
2. **評価**：誤検知（返信不要を要対応に/その逆）の許容度、通知頻度、担当割当を現場と調整。
3. **本番投入・横展開**：効果確認後に本番へ。続いて第2段・第3段。
4. **コスト管理**：API 利用量を計測し、キャッシュ・判定対象の絞り込み・上限設定で従量コストを制御。
