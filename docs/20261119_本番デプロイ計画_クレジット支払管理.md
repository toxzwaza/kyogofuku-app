## データの移し方（案Aに決定）

ローカル DB（`localdb_prod`）は本番の 10/8 ごろの写し＋クレジットの取り込み。**表をそのまま本番に流し込むことはできない**。

| 理由 | 内容 |
|---|---|
| お客様の番号がぶつかる | ローカルで取り込みが作ったお客様は id 2179〜3737。本番では 10/8 以降に予約などで同じ番号のお客様がもう作られているはず |
| 一緒に作られるデータ | お客様を作ると `customer_stages`・`referral_points` も作られる（ローカルで 788 件ずつ）。「クレジット」タグの番号も本番とローカルで違うおそれ |

ローカルで作ったお客様は 2,922−（取り込み前）＝約 790 人。うち**既存のお客様にひも付けた人が 8 人**（本番にも同じ番号でいるはず。名前で照合する）。
ローカルで画面から直したデータはない（支払済にした月 0・確認済み 0）ので、ローカルの状態は「取り込みのコマンドを流した結果」と同じ。

### 案A（採用）：ローカルから書き出して、本番で読み込むコマンドを作る
- `credit:export`（ローカル。`app/Console/Commands/ExportCreditData.php`）：取り込みで作ったお客様（名前と「クレジット」タグだけ）、既存のお客様へのひも付け（番号＋名前）、契約・支払予定・仮登録の印・スタッフ（番号＋名前）を1つの JSON に書き出す。同じ名前のファイルがあれば上書きしない
- `credit:load`（本番。`app/Console/Commands/LoadCreditData.php`）：
  - クレジットの契約が1件でもある DB には読み込まない（最初の1回だけ）
  - 取り込みで作ったお客様は**新しい番号で作り直し**、「クレジット」タグを付ける（紹介ポイントの基盤も通常どおり作られる）
  - 既存のお客様は番号と名前（空白を除く）が合うことを確かめてからひも付け。1人でも合わなければ一覧を出し、何も書かずに止まる
  - 信販会社は名前で結び付け。無い会社があれば止まる
  - スタッフは番号と名前が合うときだけ結び付け、合わなければ空にして警告（担当の表記 `staff_name` は残る）
  - 1つのトランザクションで入れ、入れた件数・金額の合計がファイルと違えば元に戻す
  - `--dry-run` は確認と件数だけ。`--map=<CSV>` でお客様の番号の対応（ローカル→本番）を書き出す
- 長所：**ローカルで確かめた結果がそのまま本番に入る**（件数で突き合わせられる）
- 短所：コマンドを新しく作る（テストつき。半日ほど）

### 案B：本番で同じ取り込みを流し直す
- 11/19 の zip から作った取り込みファイル＋指定 CSV（修正・紐付け・同名ファイル・仮登録）で、`credit:import`→`credit:provisional` を本番で順に流す
- 長所：もうあるコマンドで済む
- 短所：本番には 10/8 以降に増えたお客様がいるので、名前の一致で**ひも付け先が変わる・要確認が増える**ことがある（ローカルと結果がずれる）。紐付け指定のお客様の番号はローカルのものなので、本番の番号に書き換える。同名ファイルは2回に分ける。手順が多い

> 取り込みの元になったファイル（Excel を読んだ結果 `20261119_取り込みファイル_Excel読み取り結果.json`・紐付け指定の全件・追加確認リスト）は、11/19 に案件フォルダの `10_プロジェクト/20261106_クレジット管理移行/資料/取り込み指定/` へ写した。
